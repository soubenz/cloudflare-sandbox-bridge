# Opalix sandbox layer: implementation plan

## Context

Opalix is a hands-on learning platform for production AI engineering. Learners work in real hosted environments (a Python agent, LiteLLM, Grafana, a fake LLM provider) and either build a missing component or fix a broken system. A checker grades the outcome.

The product plan (section 15) says the sandbox layer comes first, as a standalone API, and the app frontend, backend and a command-line test client are all clients of it. This plan covers that layer only: Phase 0 (spike), Phase 1 (sandbox API), and what Phase 2 (first labs through the CLI) needs from it. The app, the lab window and the LLM fault-injection Worker are later plans; only their interface to this layer is fixed here.

**Starting point.** `soubenz/cloudflare-sandbox-bridge` is a 36-line wrapper (`src/index.ts`) around the upstream `@cloudflare/sandbox` HTTP bridge, three region configs and one patch. None of it is Opalix code. The user will clone this repo into a new Opalix repo; the work is developed on branch `claude/charming-mccarthy-49eg0a` here and carried over by that clone. Removed: the bridge wrapper, `wrangler.eu/usa/apac.jsonc`, `patches/`, `patch-package`, `PATCHES.md`, and every Ingka reference. Kept: `.gitignore`, `wrangler` and `@cloudflare/workers-types` dev deps.

**Decisions made with the user (22 Sep 2026):**

| Decision | Choice | Why |
|---|---|---|
| Code home | Clone of this repo | Keeps history, session already here |
| SDK line | `@cloudflare/sandbox@next` (1.0 preview) | Cloudflare tells new projects to start there; 1.0 GA will land during the 10 to 12 week build; avoids rewriting every exec and terminal call. Cost: no upstream bridge or WarmPool, so we write a small pool Durable Object |
| Lab images | One image per lab family | Each family is its own `Sandbox` subclass with its own Dockerfile and warm pool. Lab content is still a per-lab bundle in R2 hydrated at start, so images change rarely and labs change often |

**Routine decisions made in this plan (stated so they can be overruled):**

- Single region for launch: EU, `locationHint: "weur"`. One `wrangler.jsonc` with an `env.staging`.
- Service UIs (Grafana, LiteLLM) are proxied path-based through the Worker at `/sessions/{id}/services/{name}/`. Grafana runs with `serve_from_sub_path`, LiteLLM with `SERVER_ROOT_PATH`. Wildcard preview URLs on `*.labs.opalix.ai` stay an option later.
- Two credentials: a service bearer key (`SANDBOX_API_KEY`) for the app backend and CLI, and a short-lived HMAC session token minted by `POST /sessions` for browser-facing endpoints (terminal, events, service proxy).
- Check scripts are never resident in the container between runs. They are fetched from R2 into a root-only temp dir at check time and deleted after. The learner's shell runs as an unprivileged `learner` user.
- Outbound network from every lab container is blocked except the Opalix LLM Worker host and a package mirror, via the SDK's static `enableInternet = false` plus `allowedHosts`. Calls to the LLM Worker get credentials injected by an outbound handler, so the container never holds a key.
- One npm package (no workspaces). The CLI lives in `cli/` and runs with `tsx`.

## SDK facts this plan relies on (verified against the docs on 22 Sep 2026)

- `getSandbox(binding, id, { sleepAfter, keepAlive, containerTimeouts })`, `sandbox.destroy()`. Sleep or destroy loses all files, processes and terminals. Cold start is 1 to 3 s for small images.
- `exec(argv, { cwd, env, timeout })` returns a process handle at launch: `id`, `output()`, `logs({ follow, replay })` with cursors, `waitForPort(port, { timeout, mode })`, `waitForExit()`, `kill(signal)`. `getProcess(id)` is null after a container restart.
- `createTerminal({ command, cwd, cols, rows })`, `terminal.connect(request, { cursor })` returns the WebSocket upgrade response, `getTerminal(id)`, `terminal.resize()`. Client: xterm.js plus `SandboxAddon` from `@cloudflare/sandbox/xterm`.
- Files: `readFile`, `writeFile`, `listFiles`, `mkdir`, `deleteFile`, `renameFile`, `exists`, `watch(path)`.
- Backups: `createBackup({ dir, ttl, name, excludes, gitignore })` to an R2 bucket bound as `BACKUP_BUCKET` (also needs `BACKUP_BUCKET_NAME`, `CLOUDFLARE_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`); `restoreBackup(handle)` works on any sandbox id. A restore mounts a copy-on-write overlay that is lost on sleep.
- Outbound: `static enableInternet = false`, `static allowedHosts`, `static outboundByHost = { host: handler }`. Only ports 80, 443 and DNS pass through handlers. HTTPS is intercepted with an ephemeral CA at `/etc/cloudflare/certs/cloudflare-containers-ca.crt`.
- Errors: `ContainerUnavailableError` (retry after `retryAfterMs`), `StaleProcessHandleError` and `StaleTerminalHandleError` (container replaced, relaunch from stored command), `OperationInterruptedError`, `RPCTransportError`.
- Dockerfile: `FROM docker.io/cloudflare/sandbox:<matching next tag>`, never override `ENTRYPOINT`, provide `CMD` only. Deploy with `npx wrangler deploy --containers-rollout=immediate`.
- Instance types: `basic` 1/4 vCPU 1 GiB, `standard-1` 1/2 vCPU 4 GiB 8 GB disk, `standard-2` 1 vCPU 6 GiB, `standard-3` 2 vCPU 8 GiB. Pricing $0.000020 per vCPU-second, $0.0000025 per GiB-second.

## Pricing review: Cloudflare Containers versus GCP versus rented bare metal

Requested by the user before approving the plan. All prices checked on 22 Sep 2026. Verdict first: **Cloudflare is not the expensive option at Opalix's scale.** Container compute is about $0.05 to $0.11 per session, and the whole platform lands between about $85 and $330 a month for 300 to 3,000 sessions a month. Bare metal only wins on raw compute above roughly 2,500 sessions a month, and it buys that with ops work a solo founder does not have. The recommendation is to stay on Cloudflare for launch and keep the backend swappable (see section 3, `Backend` interface), with a cost tripwire below.

### Monthly platform cost at the product plan's volumes

Cloudflare includes two warm containers (one per family) on `standard-1` running 24 hours: about $27 each a month (memory and disk only, CPU is not billed while idle). Running the pool 12 hours a day halves that.

| Sessions a month | Cloudflare (standard-1, 2 warm) | GCP Cloud Run | GCP VMs (n2d, 2 to 4 nodes) | Hetzner (2 AX42-1 for redundancy) |
|---|---|---|---|---|
| 300 (free-lab pass mark) | about $85 | about $25 + build cost | about $270 | about €195 |
| 1,000 | about $150 | about $75 | about $270 to $410 | about €195 |
| 3,000 | about $330 | about $215 | about $410 to $540 | about €195 to €290 |

What the table does not show:

- **Cloud Run** is the cheapest serverless number but does not fit the workload. Its request timeout caps a WebSocket at 60 minutes, routing to "the learner's instance" is best-effort session affinity, there is no snapshot, no per-instance egress policy and no PTY API. Opalix would have to build the session agent, terminal, snapshots and egress control itself. That is the Phase 1 work again, on top of the SDK we get for free on Cloudflare.
- **GCP VMs** and **Hetzner** are the "cluster backend" already in the product plan (k3s, Kata, tunnel). Both mean owning: node provisioning and autoscaling, Kata or gVisor isolation, per-pod egress firewalling, a terminal and file agent, snapshots to object storage, image distribution, patching, monitoring and on-call. That is realistic at 2 to 4 weeks to build and about a day a month to run, which is 10 to 20 percent of the 25 hours a week the plan has. Hetzner is also a fixed bill whether or not anyone shows up, and the 15 June 2026 price rise more than doubled the dedicated-vCPU cloud plans.
- **Revenue check.** An individual at €39 a month who runs 20 sessions costs about $2 on Cloudflare, about 5 percent of revenue. A team seat at €349 a year is about €29 a month for the same margin. Compute is not the business risk; churn and content pace are.
- **Where Cloudflare genuinely loses.** The SDK is a preview, the container platform is young (limits per account, image size caps, no GPU), and the terminal, backup and egress features are Cloudflare-specific. Above roughly 2,500 sessions a month a dedicated box is cheaper on paper. GPU and serving labs will need the cluster backend anyway.

### Decision and tripwires

- **Launch on Cloudflare.** Use a custom instance type (0.5 vCPU, 2 GiB, 4 GB) if the spike shows LiteLLM plus Grafana fit in 2 GiB; otherwise `standard-1`. Pool target 1 per family during EU daytime, 0 at night, until the free-lab numbers are in.
- **Keep the backend swappable.** The Session DO talks to the container only through a `Backend` interface (`src/session/backend.ts`): `ensureRunning`, `exec`, `readFile`, `writeFile`, `openTerminal`, `proxy`, `snapshot`, `restore`, `destroy`. The Cloudflare implementation wraps the SDK. A `ClusterBackend` (Hetzner or GCP, k3s and Kata over a tunnel) is the same interface later. No route, manifest or CLI code changes when a family moves.
- **Tripwires to revisit the choice:** container bill above €400 a month for two consecutive months; per-session compute above €0.25; a Cloudflare limit blocking a launch lab (memory, image size, concurrent instances); or the first scale or GPU lab, which needs the cluster backend regardless.

**Cost reference (drives pool and instance choices):**

| Item | standard-1 | custom 0.5 vCPU / 2 GiB |
|---|---|---|
| One 90-minute session, CPU half active | about $0.09 | about $0.05 |
| One warm container, 24 hours a day, per month | about $27 | about $14 |

## 3. Durable Object design

### Session DO

- `class Session extends DurableObject`. JSON operations are RPC methods (`create`, `start`, `status`, `runChecks`, `restartService`, `snapshot`, `resume`, `end`, `readFile`, `writeFile`, `pushEvent`). WebSocket, SSE and the service proxy go through `fetch()` because streamed responses do not cross DO RPC.
- Backend boundary: everything in `session/*` calls a `Backend` interface (`session/backend.ts`) with `ensureRunning`, `exec`, `readFile`, `writeFile`, `listFiles`, `deleteFile`, `openTerminal`, `proxy`, `snapshot`, `restore`, `destroy`, `metrics`. `CloudflareBackend` implements it over the SDK; the family registry says which backend a family uses. A later `ClusterBackend` (Hetzner or GCP, k3s and Kata over a tunnel) implements the same interface. This is the pricing-review exit route and also what `FakeSandbox` in tests implements.
- Sandbox handle inside `CloudflareBackend`: `lib/sandbox.ts` builds `getSandbox(env[FAMILIES[family].binding], meta.sandbox_id, { sleepAfter: "15m" })` per call, with `locationHint` on the stub. `sleepAfter` is a dead-man's switch: the health alarm keeps the container alive; if the DO stops polling, the container dies on its own.
- `withRetry(fn)`: `ContainerUnavailableError` sleeps `retryAfterMs` up to 5 times; `OperationInterruptedError` and `RPCTransportError` retry once; `Stale*HandleError` triggers `recover()`.
- One in-memory `opLock` promise serialises start, resume and recover; other operations await it.

Alarm scheduler (`timers.ts`): `schedule(kind, at, ref?)` inserts and calls `setAlarm(min(at))`; `alarm()` pops all due timers, runs each in try/catch, reschedules recurring ones, sets the next alarm.

| Kind | When | Action |
|---|---|---|
| `start` | at create | run the start sequence (durable: the alarm retries if the DO is evicted mid-start) |
| `hard_warn` | expires_at minus 5 min | emit `session.expiring` |
| `hard` | expires_at | snapshot(reason=expired), destroy, `ended` |
| `idle_warn` | last_input plus idle minus 2 min | emit `session.idle_warning` unless input since |
| `idle` | last_input plus idle | if still idle: snapshot(reason=idle), destroy, `ended`; else reschedule |
| `pressure` | started_at plus at_minutes | exec argv from `/opt/lab/pressure`, emit `pressure` |
| `health` | every 15 s with SSE clients, else 60 s | health-check each service, emit on change, detect container restart |
| `metrics` | every 30 s while running | container metrics plus cost, emit `metrics` |
| `cleanup` | ended plus 1 h | drop SQL events, `deleteAll()` except `meta` and `snapshots` |

Idle input is refreshed by: terminal client frames, PUT or DELETE on files, a check run, a service restart, a service proxy request.

Recovery (`lifecycle.recover`), triggered by `Stale*HandleError`, a null `getProcess()`, or the health alarm seeing every service pid gone:
1. Mark `recovering`, emit `container.restarted`.
2. `exec(['true'])` with retry to confirm the fresh container is up on the same sandbox id.
3. Workspace is gone. If `snapshots[0]` exists, `restoreBackup`; else re-hydrate the bundle and emit an `alert` that progress was lost.
4. Relaunch every service from `services[name].spec` in dependency order, store new process ids.
5. Drop `terminal`; connected clients get a `reset` control frame and the next attach creates a fresh terminal.
6. Back to `running`.

### Pool DO

- RPC: `claim(sessionId) -> { sandbox_id, warm }`, `release(sandboxId)`, `stats()`, `prime(target?)`, `drain()`.
- `claim` pops the head of `warm`; if empty, mints `${family}-${ulid}` and returns `warm: false` (the Session does the cold start). Always records in `claimed`, then schedules a refill alarm now.
- Warm start: `getSandbox(binding, id, { sleepAfter: "20m" })`, `exec(['true'])`, record `ready_at`. The image CMD pre-imports Python deps so the page cache is warm.
- Alarm every 30 s: ping warm sandboxes older than `ping_every_s` with `exec(['true'], { timeout: 5000 })` and destroy failures; refill `target - warm.length` in batches with `Promise.allSettled`; on capacity errors set `capacity_backoff_until` 5 min out; reap `claimed` entries older than 3 h by calling `destroy()`.
- The Session DO calls `release` after `sandbox.destroy()`. The cron calls `prime()` every 5 min as a safety kick.

## 4. Route to SDK mapping

Auth: service routes require `Authorization: Bearer SANDBOX_API_KEY`. Browser routes accept `?token=`, a bearer session token, or cookie `opx_s_{id}`. Token format: `base64url(sid.uid.exp) + "." + base64url(HMAC(secret, sid.uid.exp))`, `exp = expires_at + 10 min`. The Worker verifies before DO dispatch; the DO re-checks `sid` and state.

| Route | Handler | SDK calls | Errors |
|---|---|---|---|
| `POST /sessions { lab, user_id }` | Worker: read `current` and manifest from R2, D1 insert, `SESSION.create(meta, manifest)` schedules `start`; returns `202 { id, state: "starting", token, urls }` | none yet | 404 unknown lab, 409 active session |
| `GET /sessions/{id}` | `status()` | none (cached health) | 404 |
| `WS /sessions/{id}/terminal` | DO `fetch`, relay (4.1) | `createTerminal`, `getTerminal`, `terminal.connect`, `terminal.resize` | 409 not running |
| `GET /sessions/{id}/files/{path}` | RPC | `readFile` | 404 |
| `PUT /sessions/{id}/files/{path}` | RPC | `writeFile`, then `exec(['chown', 'learner', path])` | 413 over 2 MB |
| `GET /sessions/{id}/files?path=` | RPC | `listFiles` | |
| `DELETE /sessions/{id}/files/{path}` | RPC | `deleteFile` | |
| `POST /sessions/{id}/checks { only? }` | RPC, synchronous, progress on SSE | section 6 | 409 run in progress |
| `GET /sessions/{id}/events` | DO `fetch`, SSE with `Last-Event-ID` | none | |
| `POST /sessions/{id}/events` (service key) | RPC `pushEvent` | none | used by the LLM Worker to push `cost` and `llm.call` events |
| `POST /sessions/{id}/services/{name}/restart` | RPC | `getProcess(id)?.kill(15)`, 5 s, `kill(9)`, `exec(spec)`, `waitForPort` | 404 unknown service |
| `ANY /sessions/{id}/services/{name}/*` | DO `fetch` proxy (4.3) | container-port fetch, `wsConnect` on upgrade | 502 port down |
| `POST /sessions/{id}/snapshot` | RPC | `createBackup` | 409 not running |

### 4.1 Terminal WebSocket inside the DO

A DO-mediated relay, not the SDK response passed straight through.

- Client side: `WebSocketPair`, `ctx.acceptWebSocket(server, ['terminal'])` (hibernation API), attachment `{ kind: "terminal", sid }`.
- Upstream side: `terminal.connect(new Request(url, { headers: { Upgrade: "websocket" } }), { cursor })`, accept the returned socket, hold it in memory, relay both ways. The upstream socket keeps the DO resident while a terminal is attached, which is acceptable (DO duration for a 2 h session costs fractions of a cent) and unavoidable since the container RPC is live anyway.
- Why relay: every client frame updates `last_input_at`, auth is checked once, cursors are kept for reconnect, re-attach after a container restart is transparent, and the CLI gets raw bytes without depending on `SandboxAddon`'s URL scheme.
- On upstream close or `StaleTerminalHandleError`: store the cursor, `recover()` if the container is gone, else `getTerminal(id)` and reconnect; send a `reset` control frame to clients.
- Protocol: binary frames are raw bytes; text frames starting with `\x01` are control (`resize`). Browser uses `SandboxAddon` with `reconnect: true` if its URL builder can target our path (risk R6); otherwise the app ships a 40-line attach addon.

### 4.2 SSE inside the DO

- `emit(type, data)` inserts into SQL `events`, trims to 1000, writes `id: {seq}\nevent: {type}\ndata: {json}\n\n` to every open writer, removes dead writers.
- `GET /events` replays rows with `seq > Last-Event-ID` (or the last 50), then streams live with a 20 s ping comment. If keeping the DO awake for SSE becomes a cost concern, the browser channel moves to a hibernatable WebSocket without changing the event model.

Event types: `session.state`, `session.expiring`, `session.idle_warning`, `service.health`, `container.restarted`, `pressure`, `check.started`, `check.result`, `check.finished`, `snapshot.created`, `metrics`, `cost`, `llm.call`, `alert`.

### 4.3 Service proxy

- Services are launched with the session-specific prefix (`GF_SERVER_ROOT_URL={{session.base_url}}{{service.prefix}}/`, `GF_SERVER_SERVE_FROM_SUB_PATH=true`, LiteLLM `SERVER_ROOT_PATH={{service.prefix}}`), so the proxy forwards the path unchanged. `Location` and cookie `Path` are rewritten only if a service ignores its prefix.
- Strip the `token` query param and our cookie; add `X-Forwarded-Prefix` and `X-Forwarded-Proto`. First hit with `?token=` answers `302` to the same URL minus token with `Set-Cookie: opx_s_{id}=...; Path=/sessions/{id}/; HttpOnly; Secure; SameSite=None`.
- Upgrade requests use `wsConnect(request, port)`; everything else is a container-port fetch to `spec.port`. 502 with the current `service.health` if the port is down.

## 5. Session start sequence (`lifecycle.start`, from the `start` alarm)

1. `POOL(family).claim(sid)`, store `sandbox_id`, emit `session.state starting`.
2. `exec(['true'])` with retry; record `start_ms` (the cold path waits here).
3. Hydrate: get `workspace.tgz` from R2, deliver it into the container, extract to `/workspace`, `chown -R learner`. `private.tgz` goes to `/opt/lab` (root, 0700) for pressure scripts. Delivery is `writeFile` of the archive, or, if the spike shows binary writes are slow (risk R3), `curl http://bundles.opalix.internal/...` intercepted by an outbound handler that streams from R2.
4. Env: write `/etc/opalix/session.env` with `OPALIX_SESSION_ID`, `OPALIX_SESSION_TOKEN`, `OPALIX_BASE_URL`, `LLM_BASE_URL`, plus manifest `env`.
5. Services in `depends_on` order: `exec(spec.argv, { cwd, env })`, store ids, `waitForPort(port, { timeout, mode })`. On timeout emit `service.health unhealthy` with a log tail and continue; the session stays usable and status shows the failure.
6. `createTerminal({ command: ['su', '-l', 'learner', '-s', '/bin/bash'], cwd: '/workspace', cols: 120, rows: 30 })`, store it.
7. Schedule `hard`, `hard_warn`, `idle`, `idle_warn`, one `pressure` per manifest event, `health`, `metrics`.
8. `state = running`, `started_at`, `expires_at = started_at + timeout_minutes`; D1 update; emit `session.state running`.
9. Any failure: emit `alert`, `end('error')`, D1 update.

Clients wait for `session.state running` on SSE or poll status.

## 6. Checker runner (`checks.ts`)

1. `run_id = ulid()`, `dir = /run/opalix/checks-{run_id}` (root, 0700). Fetch `private.tgz` from R2 and extract there.
2. Emit `check.started { run_id, total }`.
3. Per check, sequential unless `parallel: true`: `exec(['bash', script], { cwd: '/workspace', env: { OPALIX_CHECK_NAME }, timeout })`, plus an own timer that calls `kill(9)`; `waitForExit()`, `output()`.
4. Parse: exit 0 is a pass. `message` is the last stdout line; if it parses as JSON `{ pass, message, details }` that wins. On failure append 1 KB of stderr tail. Result: `{ name, pass, message, duration_ms, exit_code, timed_out, weight }`.
5. Emit `check.result` per check; `rm -rf dir` in `finally`; emit `check.finished { run_id, passed, total, score }`; store `checks:last`; insert `check_runs`; return the results.
6. Hiding: the terminal runs as `learner`; the check dir is root-only and short-lived; scripts never touch `/workspace`; `ps` shows the path, not the content.

## 7. Snapshot and resume

- `snapshot(reason)`: `createBackup({ dir: '/workspace', ttl: 7 days, name: '{sid}-{n}', excludes: ['**/.venv', '**/node_modules', '**/__pycache__'], gitignore: true })`, push onto `snapshots`, insert into D1, emit `snapshot.created`. Runs on explicit call, expiry, idle kill, and user end.
- `resume()`: allowed when `ended` (or `running` with `force` to roll back). Same session id. Claim a new sandbox, `exec(['true'])`, `restoreBackup(snapshots[0])` instead of extracting `workspace.tgz` (`private.tgz` still hydrated), env, services, terminal, timers with a fresh budget, `resumed_count++`, new token returned.
- Caveat: a restore is a copy-on-write overlay lost on sleep. Sleep already loses everything, so the fence is unchanged, but the health alarm must never let the container idle past `sleepAfter`, and snapshotting a restored workspace must be verified to capture the merged view (risk R4). Fallback: extract the backup archive into `/workspace` with `tar` instead of `restoreBackup`.

## 8. Egress policy per family (`families/agent-lab.ts`, same shape for gateway)

```ts
export class AgentLab extends Sandbox<Env> {
  static enableInternet = false;
  static allowedHosts = [LLM_HOST, MIRROR_HOST, BUNDLES_HOST];
  static outboundByHost = { [LLM_HOST]: llmOutbound, [MIRROR_HOST]: passthrough, [BUNDLES_HOST]: bundlesFromR2 };
}
```

- `llmOutbound` sets `Authorization: Bearer env.LLM_WORKER_KEY` (never seen by the container) and forwards `X-Opalix-Session` and `X-Opalix-Session-Token`, which the container sets from `/etc/opalix/session.env`. The token is `HMAC(SESSION_TOKEN_SECRET, sid)`, so a learner cannot impersonate another session; the LLM Worker verifies it with the shared secret. If the spike shows handlers receive the sandbox id in `ctx` (risk R2), inject the session id from a lookup instead and drop the token.
- Containers use plain `http://` to these hosts so the ephemeral CA is not needed; `opalix-init.sh` still installs the CA for anything that uses HTTPS.
- `allowedHosts` is static, so per-lab extras come from `manifest.egress.allow[]` via `setAllowedHosts` at start.
- Interface fixed for the later LLM Worker: it receives those two headers, validates the token, and pushes `cost` and `llm.call` events to `POST /sessions/{id}/events` with the service key.

### Bugs found and fixed

1. **`BASE_URL` never reached the tests.** Vite defines
   `import.meta.env.BASE_URL` from its `base` option and vitest backs
   `import.meta.env` with `process.env`, so the shell value was overwritten
   with `/`. Renamed to `OPALIX_URL`; the config now throws when unset.
2. **Check scripts ran without the lab's env** — graders could not assert
   on their own lab's configuration.
3. **`manifest.env` reached nothing at all.** Not services, not pressure
   scripts, not the terminal; and `/etc/opalix/session.env` was written but
   read by nothing. `su -l learner` wipes the environment anyway. The
   `hello` lab asks the learner to write `$GREETING` to a file — in their
   shell it was empty, so **the lab was unsolvable**. Fixed at the source
   with one `applySessionEnv` (setEnvVars + env file + `/etc/profile.d`
   drop-in) used by start, resume and recover.
4. **Errors raised in the Session DO lost their HTTP status.** Workers RPC
   keeps only `name` and `message`, so every documented 404 arrived as a
   500. `ApiError` now encodes status and code in its `name`.
5. **SDK not-found / too-large / exists errors** mapped to 500 rather than
   404 / 413 / 409.
6. **`egress.allow` replaced the base allowlist** instead of extending it —
   a lab declaring one extra host silently lost the LLM worker, the package
   mirror and the bundle server. Now a union, and re-applied on resume and
   recover (both claim a fresh sandbox).
7. **A check run did not reset the idle clock**, contradicting `docs/api.md`.

### Open

- **Terminal websocket 500s** with `SandboxSecurityError: "Terminal
  connection is not authorized"` — the SDK requires a route token minted by
  its own client wrapper, and our DO-mediated relay is not obtaining it.
  This is risk **R5**, and it has never worked. Under investigation.
- **`hints[]` is entirely unimplemented**: no timer kind, no event type,
  nothing scheduled, and `status()` never returns the manifest, so a client
  cannot render them either. A schema field with zero runtime.
- **Periodic health checks never re-check the port** — only whether the
  process exists. A service that binds its port then wedges stays
  `healthy` for the whole session, so `healthcheck.type/path` is honored
  exactly once, at start.
- **Templating covers only `env`, `services[].argv/cwd/env`, and

  literal `{{session.base_url}}`), not `egress.allow`, not
  `healthcheck.path`, not `hints[].text`.
- **`services[].ui` does not gate the proxy** — it only filters the
  advertised URL map, so a `ui: false` service with a port is still
  reachable by anyone holding the session token.
- **`depends_on` order is not enforced on relaunch** after a container
  restart; it relies on object insertion order surviving DO storage.
- **`topoOrder` miscounts a duplicated `depends_on` entry** and reports a

- Tiers 3 and 4 are written (`timing.test.ts`, `egress.test.ts`, with

  on the terminal, since that is the only route that runs commands.

## 17. Second round: what the terminal, the audit and the measurements found

### The terminal (risk R5) was three bugs stacked

Each one hid the next, and none was visible without running it:

1. We passed `terminal.connect()` a synthetic upgrade request carrying only
   `Upgrade: websocket`. The SDK client validates just that header, but the
   Sandbox DO takes its WebSocket branch only when `Connection: Upgrade` is
   also present; otherwise the request falls through to `containerFetch`,
   which rejects `/ws/terminal` on the control port unconditionally. The
   error said "Terminal connection is not authorized", which sent the first
   investigation at the route-token machinery — that part worked all along.
2. The container's PTY has its own framing: JSON text frames for control
   (`ready`, `chunk`, `truncated`, `error`, `exit`), each `chunk` followed
   by one binary frame, and client input read as raw binary. We forwarded
   everything verbatim, so a learner would have seen literal JSON and had
   their keystrokes parsed as control messages.
3. Upstream binary frames arrive as `Blob`, and `WebSocket.send()` coerces a
   Blob to the string `"[object Blob]"` instead of sending bytes. Output
   reached the client as that literal text, once per chunk.

The fix for all three is small; finding them needed a live deployment,
since none reproduces without Docker.

### The env fix was resting on a guarantee the SDK does not give

`setEnvVars` writes an in-memory field on the Sandbox DO that nothing
restores after an eviction — the DO's `blockConcurrencyWhile` reloads
`sandboxName`, `keepAlive` and `containerTimeouts`, but not `envVars`.
Evictions are routine while the container keeps running, so `recover()`
never fires. A service restarted mid-session, or any pressure script,
would have launched with none of the lab's env and no error. The rendered
env is now stored in the Session DO and passed explicitly to every exec.

Worse, making `/etc/opalix/session.env` sourced by every login shell turned
manifest env **keys** into code: they were interpolated raw, so `MY-KEY`
broke shell startup silently and a key containing a backtick would execute
as the learner on every attach, from lab-author-controlled input. Keys are
now validated as shell identifiers at publish time.

| Cold start (n=10) | 7 467 ms | 21 355 ms | 3 500 | 21 355 |

## 18. Third round: persistence, and a deploy hazard

### The learner's shell did not survive anything

Probed directly: set a variable, `cd` somewhere, detach, re-attach — cwd
back to home, variable gone. The container's PTY server ties shell
lifetime to its websocket ("Session terminated, killing shell..."), and
that connection drops on a closed tab and on any Durable Object eviction.
The SDK never terminates a terminal itself, so the relay could not hold
onto it. The shell now runs inside a named tmux session
(`new-session -A`), so an attach joins the existing session or starts it:
cwd, environment, scrollback and any running command survive. Verified:
after a detach and re-attach, `pwd` is still `/tmp` and the marker
variable is intact.

A related bug found on the way: when the upstream dropped under a
still-attached client, `handleClientMessage` forwarded input only while
the socket was open, so every keystroke was silently discarded and the
terminal just stopped responding. Input now reconnects first.

### Warm containers outlive the image they were built from

The first run after the tmux deploy still got a terminal that died
instantly: the session was handed a **warm container started from the
previous image**. A warm container keeps whatever image it booted with,
the ping loop keeps it alive indefinitely, and nothing about a warm claim
says which image is inside — so an image rebuild keeps being quietly
undone for whoever draws that container. Draining by hand fixed it, which
is not something to rely on. Warm containers are now recycled past 30
minutes, which bounds staleness without the pool needing to know the
deployed version.

**This is worth remembering for every future image change**, and it is
the strongest argument yet for the pool exposing `drain` (now routed) and
for CI draining after a deploy once a service key is available to it.

### Also closed this round

- `hints[]` implemented rather than removed: timers scheduled on start and
  resume, emitting a `hint` event with index and text.
- Services relaunch in topological order after a container restart, rather
  than relying on object insertion order surviving DO storage.
- CI reports image sizes, so the spike's one unanswered number fills in on
  the next deploy.

### Remaining

- **Snapshot and resume are still untested** — blocked on R2 access keys.
  This is the last untested path in the layer.
- `services[].ui` gates URL discovery but not the proxy, so a `ui: false`
  service with a port is still reachable by the session owner. A decision,
  not a bug: gating it could break a lab that proxies a non-UI service.

## 20. Fourth round: the console, and what exercising the gateway found (24 Sep 2026)

A lab console (separate Worker, `opalix-dashboard`) was built, driven in a
real browser with Playwright, and the gateway family was exercised end to
end for the first time. Between them they found eleven more bugs. Three
were live security or data-loss defects.

### The serious ones

- **Path traversal on the files API.** Hono matches `:path{.+}` against the
  *encoded* path and decodes afterwards, so `%2F` and `%2E` survive
  routing: `files/..%2F..%2Fetc%2Fpasswd` reached the handler as
  `../../etc/passwd`. Plain `../` is normalised away by the URL parser and
  404s, which is exactly why the obvious probe said the routes were safe. A
  session token was enough to read *and write* anywhere in the container,
  including `/etc/opalix/session.env` (the LLM token) and
  `/etc/profile.d/opalix.sh` (sourced by every login shell).
- **"Recovery" silently destroyed the learner's work.** The health alarm
  declared a container restart whenever every process handle came back
  null, and `recover()` then re-hydrated the published bundle over
  `/workspace`. The SDK implements `getProcess` as
  `runExisting({ kind: "current" })`, which does not wake the container and
  returns null for every id when the runtime has re-incarnated — so the
  signal meant "not the same runtime", not "the processes died". Observed
  firing twice in one session while Prometheus was healthy and answering
  its port. Now corroborated by a direct port probe, and `recover()`
  refuses to re-hydrate over a workspace that still has files in it.
- **`services[].ui` did not gate the proxy**, only URL discovery, so a
  `ui: false` service with a port was reachable by any token holder.

### The gateway family had never run

- **Grafana cannot bind its default port.** 3000 belongs to the
  `@cloudflare/sandbox` control plane; stock `grafana.ini` binds 3000 and
  `grafana-server` dies with "address already in use". Fixed in both
  images. The agent image had the same latent bug.
- **The manifest accepted ports the SDK rejects** (`80`, `443`, `3000`),
  moving the failure from publish to session start. Duplicate ports and
  `ui: true` with no port were also only discoverable in a container.
- **`logs_tail`** — the one field that explains a failed service start —
  was `JSON.stringify` of a `Uint8Array`, i.e. 1 KB of the digits of a byte
  array.
- **A check that exceeded its timeout reported `timed_out: false`.**
- **Terminal re-attach reused a dead PTY.** `connect()` on a dead terminal
  upgrades successfully, so the relay held an open upstream that emitted
  nothing and never fired `close`. Confirmed on agent by killing the PTY
  with `tmux detach-client`; a resize against the dead terminal *succeeded*
  with no alert.

### Measured

| | |
|---|---|
| Agent cold start (warm hit) | 2.5 s |
| Gateway cold start (genuine cold miss) | 9.7 s |
| Container-only start, gateway / agent | 2.1 s / 2.6 s |
| Image size, agent / gateway | 2.17 GB / 2.16 GB |

Biggest layers: LiteLLM 531–621 MB, Grafana 473 MB, Prometheus 287 MB.
**The image is not the cold-start cost** — the gateway image boots
marginally faster than agent's. The 9.7 s is service boot, almost all of it
Grafana's sqlite migrations. `startAllServices` is sequential and blocks on
each `waitForPort`, so time-to-`running` is the *sum* of all healthchecks.
This corrects section 19's claim that image size drives the cold-start
swing.

### Environment limits learned (not product faults)

- This sandbox's egress proxy re-issues requests and strips `Upgrade`, so a
  browser WebSocket to the API 400s. Proven from the Worker's own error
  enumerating received headers; a direct Node `ws` client connects and gets
  a real PTY. Needs `OPALIX_E2E_NO_WEBSOCKETS=1` per environment, never
  inferred.
- **`/dev/sessions` fences on hashed client IP and the proxy rotates
  addresses.** This leaked containers three separate times today and makes
  the Playwright suite's own teardown unreliable. The per-IP dev identity
  needs replacing, not working around.

### Still open

- Snapshot/resume: still the only untested path, still blocked on R2 keys.
- Input sent in the window around a terminal upstream drop is silently
  discarded: a socket whose peer has gone still reads `OPEN`, so `send()`
  is a no-op. Needs an ack or keepalive, not a `readyState` check.
- Gateway runs on `standard-1`, which is **0.5 vCPU** (`src/session/metrics.ts:14`,
  and the SDK-facts table above) -- not the 1 vCPU claimed twice below and in
  briefings; corrected 25 Sep. A scale lab would run the load
  generator and the system under test on one core, so the numbers would
  teach CPU starvation.
- Workspace files are never templated, so a lab pointing one service at
  another's proxied prefix must substitute placeholders itself.
- CI does not drain the pool after an image deploy: a warm container keeps
  whatever image it booted with. Needs `SANDBOX_API_KEY` as a repo secret.

### 21.1 The model layer

Map the catalogue's three modes onto one architecture:

| Mode | Implementation |
|---|---|
| **Scripted** | A deterministic fake service in the lab's own `workspace/`. No network. What `duplicate-emails` already does. |
| **Real** | AI Gateway's OpenAI-compatible endpoint, `https://gateway.ai.cloudflare.com/v1/{account}/{gateway}/compat/chat/completions`, backed by Workers AI. |
| **Real plus faults** | The same gateway, but pointed at a lab-local fake through **AI Gateway Custom Providers**. Real retries, caching, logging and fallbacks wrap an upstream we control. |

That last row is the important find: it gives real gateway behaviour around
injected faults, which is exactly what Path 1 and Path 3 need and what
neither a pure fake nor the real gateway alone can provide.

**Wiring.** `LLM_HOST` becomes `gateway.ai.cloudflare.com`, and
`llmOutbound` (`src/families/egress.ts`) injects the credential so the
container never holds it — the mechanism already built and tested.

**Settled by the spike, and the docs had it backwards** (see the AI Gateway
section of `docs/spike.md`). For a Workers AI model on `/compat`,
`cf-aig-authorization` alone returns **401** and plain `Authorization`
returns **200**. `cf-aig-authorization` applies only to gateways with
authenticated-gateway mode on, which ours is not.

So `llmOutbound` needs **no change** — its existing `Authorization: Bearer`
injection is already correct. The "correction" this plan originally called
for would have broken every Real-mode lab, which is precisely why the spike
ran before any lab was written.

**Do not build on:** the Universal Endpoint (deprecated — use `/compat`, and
Dynamic Routing for fallbacks, not the array form), or AI Gateway
**Evaluations** (deprecated and *unavailable on new accounts*). Path 4 must
build its own eval harness in-lab. The catalogue's P4 labs never assume
otherwise, so this costs nothing — but it would have been an expensive
assumption.

### 21.2 Determinism, which is the whole grading problem

A grader cannot depend on a model's wording. `temperature: 0` plus `seed`
reduces variance but is **not** a guarantee on batched fp8 inference.

The guarantee is the **cache**: key is SHA-256 of provider + path + model +
provider auth header + the complete request body, exact match, returning a
byte-identical response with `cf-aig-cache-status: HIT`.

House pattern for every Real-mode lab:

- Pin the request body; set an explicit `cf-aig-cache-key` (lab id + step id)
  and `cf-aig-cache-ttl: 86400`; pre-warm at publish time; assert `HIT`.
- Anything per-learner goes in `cf-aig-metadata` (max 5 entries), which is
  **not** part of the cache key.
- Where a step cannot be cached, assert on shape or JSON schema, never
  wording.

Caveats that will bite: **streaming responses are not cached**, so streaming
labs (P1-07) assert structure only; the injected credential is part of the
cache key, so **rotating `LLM_WORKER_KEY` flushes every cached lab response
at once**; concurrent identical requests can both MISS; default TTL without
an explicit one is 5 minutes, far too short for a session.

### 21.3 What graders read

- **Synchronously, from response headers**: `cf-aig-cache-status`,
  `cf-aig-step` (which fallback leg served), `cf-aig-log-id`, `cf-aig-dlp`.
- **Tokens, cost, duration**: the logs REST API or the Worker binding's
  `getLog()`. Capture `cf-aig-log-id` from the response and poll that id with
  backoff — **log ingestion latency is undocumented**, so a grader that reads
  immediately can race.
- Cost is an **estimate**, and a cache hit always records `cost: 0`. Grade
  "cost went down", never an exact figure. This directly shapes P1-02, P3-03
  and P1-07.

### 21.4 Cost and capacity

Workers AI bills in Neurons: **$0.011 per 1,000**, with 10,000/day free.
A 500-in/300-out call on `llama-3.1-8b-instruct-fp8` is ≈14.7 neurons —
**about $0.00016, one-sixtieth of a cent**. Per-learner model cost is noise
next to the ~$0.09 container.

The free allocation is **per account per day, shared** (~680 calls), so it is
irrelevant at cohort scale: budget for Workers Paid.

**The real ceiling is rate limits, and they are per account, not per
learner:** 300 requests/minute for text generation; 20/min for frontier
models. Design every lab against a small `@cf/` model and treat frontier
models as demo-only. Also: **10 gateways per account (20 paid)** — a gateway
cannot be per-lab or per-learner, so segment with `cf-aig-metadata` and
spend-limit rules.

## 23. Closing the open session endpoint (implementation)

### Context

`DEV_OPEN_SESSIONS=1` means anyone with the console URL can start containers
on the account. It was always meant to be temporary. Section 22 proposed
Cloudflare Access in front of a dashboard Worker, but Access defines
applications on hostnames in a zone the account controls, and the account
holds `mlopshero.com`, `secondpacket.com` and `silknova.ai` — **not**
`opalix.ai`, and `workers.dev` is not a zone anyone can attach a policy to.
So Access would have blocked on a registrar change.

The user chose instead: skip Access, gate the console behind a password page
in its own Worker, single user for now. That needs no domain, no identity
provider and nothing outside this repo, and it closes the hole today. It is
explicitly interim — no per-person revocation, no SSO — and the shape leaves
room to put Access in front later without touching the API.

### 23.1 API: replace the open route rather than relax it

- **`POST /sessions/start`** — new, **service key required**, body
  `{ lab, user_id }`. Rejoin-or-create: reuses `activeSessionFor` and
  `rejoinSession`, which already exist for this exact purpose, and falls
  through to `createSession`. This is the old `/dev/sessions` handler with
  its identity guessing removed.
- **`POST /sessions` stays strict-create** (409 on a second active session).
  The CLI and `routes.test.ts` assert that 409; the two routes differ only
  in whether a conflict is an error or a rejoin.
- **Delete `POST /dev/sessions`**, `DEV_OPEN_SESSIONS` (from `src/env.ts`
  and **both** `wrangler.jsonc` blocks — `vars` are not inherited by named
  environments, so staging must be flipped separately),
  `requireServiceAuthUnlessOpen`, the client-id branch and `shortHash`
  (whose only two callers go with it).
- **The per-IP cap must be deleted, not carried over.** This is a hard
  break rather than dead code: every call now originates from the dashboard
  Worker, so `CF-Connecting-IP` is the fleet's address, not a learner's. A
  cap of 2 would count every user as the same address and wedge the whole
  system at two live sessions. Remove `DEV_SESSIONS_PER_IP` and
  `activeSessionsForIp`.
- `/labs`, `/labs/:slug`, `/pools`, `/pools/:family` become
  **service-key-only**, since `requireServiceAuthUnlessOpen` is what made
  them open. `GET /labs` is the one that matters: it is the console's first
  screen, before any session exists, and it is proxied (§23.2).
- **`0003` migration drops `sessions_active_ip`.** `ip_hash` is written only
  by the route being deleted, so the index becomes dead weight one day after
  landing. Keep the column (dropping one in D1 is awkward and it costs
  nothing); drop the index rather than leave it as a puzzle.
- **A router-level auth-matrix test**, because nothing in CI can catch this
  regression: the unit suite never builds a router and the integration
  suites all carry a service key, so both stay green whatever the flag does.
  Assert the expected status for each route with no credential, a session
  token, and a service key.

### 23.2 Dashboard becomes a Worker with a password gate

`dashboard/` stops being assets-only.

- **`dashboard/src/worker.js`** — a plain fetch handler, no Hono, no
  dependencies. Routes:
  - `POST /auth/login` — constant-time compare against `CONSOLE_PASSWORD`,
    then set `opx_console`, an HttpOnly, Secure, SameSite=Lax cookie holding
    an HMAC-signed `{sub, exp}`. **Reuse the exact token shape from
    `src/auth.ts`** (`hmac`, `base64url`, `timingSafeEqual`,
    `mintSessionToken`/`verifySessionToken`) rather than inventing a second
    one — copy it into the dashboard bundle, since the two Workers do not
    share code today.
  - `POST /auth/logout` — clear the cookie.
  - `GET /api/labs` → proxies `GET /labs` with `SANDBOX_API_KEY`.
  - `POST /api/start` → proxies `POST /sessions/start` with the key and
    `user_id` from the cookie's `sub`.
  - anything else → valid cookie serves `env.ASSETS.fetch(request)`; no
    cookie serves the login page (200, not a redirect, so a deep link still
    lands somewhere sensible). `/api/*` without a cookie is a 401, not a
    login page, so a stale tab fails loudly rather than rendering HTML into
    a JSON parser.
- **`sub` is a fixed subject** (`console`) rather than per-browser. One
  person, so one active session at a time is the behaviour we want, and it
  makes the D1 `sessions_active_user` fence mean exactly that. A second tab
  rejoins rather than starting a second container.
- **The login page is inline in the Worker**, not an asset — it has to be
  servable before auth, and assets are behind the gate.
- **Secrets**: `SANDBOX_API_KEY`, `CONSOLE_PASSWORD`, `CONSOLE_COOKIE_SECRET`
  (all `wrangler secret put`, none in the repo). **Var**: `API_BASE`.

### 23.3 Wiring

- `dashboard/wrangler.jsonc` gains `"main"` and
  `"assets": { "directory": "./public", "binding": "ASSETS",
  "run_worker_first": true }`. Verify that key against wrangler 4.102's
  schema at implementation time; if it has moved, the Worker must still see
  every request before assets do, or the gate is decorative.
- `dashboard/build.mjs` also bundles `src/worker.js`, **outputting outside
  `public/`** — a worker bundle inside the assets directory would be served
  as a static file.
- `dashboard/src/api.js`: `labs()` → `/api/labs` and `startSession()` →
  `/api/start`, both same-origin, so those two stop needing CORS. Everything
  else (status, files, checks, events, terminal, service proxy) keeps going
  straight to the API with the **session token** and stays cross-origin, so
  `DASHBOARD_ORIGIN` still matters. The `clientId()` work stays for the
  localStorage resume path but is no longer an identity.
- The operator panel keeps asking for a pasted service key for pool actions;
  proxying that through the Worker would hand pool control to anyone who
  knows the console password, which is a different trust level.

### 23.4 Keeping the browser suite working

`test/e2e/fixtures.ts` logs in once per context: `POST /auth/login` with
`OPALIX_CONSOLE_PASSWORD` before the first navigation, so the cookie is in
the Playwright context. No unauthenticated path is reintroduced for tests.

Two defects were found and fixed before it met a learner, both of the same
kind — a lab that punishes the wrong thing:

- **The lab let its own wrong answer pass.** The solution's docstring warns
  against keying the idempotency header on a hash of the drafted body
  "because the draft is re-run on every attempt", but the model stub was
  deterministic, so that hash was stable and the wrong answer passed. A
  learner would have shipped a fix that breaks the moment a real model
  varies its wording, with a green check confirming it. The stub now
  rotates its phrasing per call.
- **It failed a learner for touching an unrelated file.** The injected 503
  was keyed to a `Ticket ID:` line parsed out of the prompt, so reformatting
  `agent/llm.py` disabled the faults and `retries-still-happen` failed them
  with a message about missing retries. The id is now found anywhere in the
  prompt.

**The rule both point at:** a grader that only rejects the untouched
workspace is not a grader. Every lab is verified against four workspaces —
untouched, solution, and the two plausible wrong answers — before it ships.

### The open session endpoint is closed

`POST /dev/sessions` returned 202 to anyone with the URL. Now 404; `/labs`
and `/pools` are 401 without a key; the console sits behind a password in
its own Worker holding the service key, and even a direct asset request
signed out returns the login page. `POST /sessions/start` replaces the
deleted route — same key, explicit `user_id`, rejoin-or-create — while
`POST /sessions` stays a strict create for the CLI.

Three things this taught:

- **A Worker cannot `fetch()` another Worker over workers.dev** — Cloudflare
  answers error 1042. Sign-in worked, the page loaded, and every proxied
  call failed with a plain-text Cloudflare body. No dry run, typecheck or
  unit test could see it. It is a service binding now.
- **Cloudflare Access was not available**: it defines applications on
  hostnames in a zone the account controls, and `opalix.ai` is not on this
  account at all (`mlopshero.com`, `secondpacket.com`, `silknova.ai` are).
  The password gate is interim and its limits are real.
- **CI could not have caught this class of regression.** The unit suite
  never builds a router; every integration suite carries a service key. Both
  stayed green whatever the auth was. `test/unit/auth-matrix.test.ts` now
  asserts which credential each route demands and that nothing but `/health`
  is ungated.

### The AI Gateway spike contradicted the plan

Run before any Real-mode lab, and it was right to be. The docs present
`cf-aig-authorization` as the gateway credential and warn that
`Authorization` is the top cause of 401s; for Workers AI on `/compat` it is
the reverse — `cf-aig-authorization` alone returns **401**, plain
`Authorization` returns **200**. Section 21 had called for exactly that
change; it would have broken all 20 Real-mode labs.

Also measured: the cache does give byte-identical repeats, but the explicit
cache-key path needed **two** sequential repeats before `HIT`, so graders
pre-warm and treat a MISS as a retry. Logs carry tokens, cost and duration
about 2 s after the call. Full numbers in `docs/spike.md`.

`manifest.ts` told lab authors that ports below 1024 are unavailable

`chown -R learner /workspace` and `su -l learner` both work. The message now
states the rule without a cause we would be guessing at; the likeliest
reconciliation is a missing `CAP_NET_BIND_SERVICE`, which is unproven.

## 28. Admin panel (planning round, 26 Sep 2026)

### Context

Opalix has three Workers today: the sandbox API (`src/`, service-key or
session-token auth, no browser UI), the learner-facing console
(`dashboard/`, its own Worker with a shared password cookie `opx_console`
holding `SANDBOX_API_KEY` server-side, plus an "operator panel" that asks
a human to paste the raw service key into the browser for pool
prime/drain), and the marketing site (`site/`, assets-only, zero
bindings, whose `/waitlist` link 404s today). There is no admin surface
anywhere.

The user asked to plan (not yet build) an admin panel covering exactly
four areas: **lab catalogue management, usage & cost, user/account
management, and a waitlist view**. Two scoping decisions were made with
the user before designing further:

1. **User/account management stays lightweight.** There is no real
   per-person account system today — `dashboard/src/worker.js` hardcodes
   the subject `'console'` for every learner, and D1's `user_id` is a
   session-fencing key, not an identity. The admin panel's "users" area is
   scoped to what exists: a session/activity view keyed on `user_id` as
   D1 already has it. Real accounts/login/signup are explicitly out of
   scope for this plan.
2. **The waitlist view is designed against an assumed schema.** No
   waitlist backend exists anywhere in this repo (`site/` has zero
   bindings; `/waitlist` 404s), and its real backend is likely being
   built by a separate session. This plan proposes a placeholder D1 table
   so the admin *view* can ship independently, explicitly flagged as
   provisional and not binding on whatever the real backend turns out to
   be.

Two things this section relies on that don't exist yet, both addressed
below: `CostState` (`src/session/state.ts`) lives only in ephemeral
Durable Object storage and is never persisted to D1 or exposed via any
route; and there is no admin-tier auth anywhere (every route is gated by
either the service key or a per-lab-session token).

### Where it lives, and why

**A new small Worker, `admin/`, sibling to `dashboard/`, cloning its
proven shape**: own `wrangler.jsonc`, own password + HMAC cookie, a
`services` binding to `opalix-sandbox` (same pattern as `dashboard/`'s
`API` binding), a same-origin `/api/*` proxy, static assets under
`admin/public/`.

Rejected: folding it into `dashboard/` (mixes learner-trust-tier code
with founder-only operations on one origin, growing the blast radius of
a leaked console cookie); a new `/admin/*` route group directly in
`src/router.ts` (that Worker is a pure API surface with no HTML/cookie
machinery anywhere in it — the *data* routes belong there, gated by
`requireServiceAuth` exactly like `/pools` and `/users/:uid/sessions`
already are, but the browser-facing login/cookie/proxy layer doesn't);
bolting onto `site/` (deliberately assets-only, zero bindings, stated
intent to stay that way).

### Auth model

**A new, separate admin password + cookie in `admin/src/worker.js`** —
not a reuse of the operator panel's "paste the raw service key into the
browser" pattern. Copy the exact HMAC/cookie construction
`dashboard/src/worker.js` already uses (`COOKIE = 'opx_console'`, a local
`hmac()` helper, `CONSOLE_COOKIE_SECRET`, `CONSOLE_PASSWORD`, all
confirmed at `dashboard/src/worker.js:18,38,62,76,181`) under new names:
cookie `opx_admin`, secrets `ADMIN_PASSWORD` and `ADMIN_COOKIE_SECRET`.
Same interim caveat as the console's own: one shared secret, no
per-person revocation, no SSO.

The operator panel's pattern exists because the console password is a
*lower* trust tier than the service key (proxying pool ops through it
"would hand pool control to anyone who knows the console password"). The
admin panel inverts that: `ADMIN_PASSWORD` is meant to *be* the high
trust tier, so `admin/src/worker.js` can hold `SANDBOX_API_KEY` server-side
and do a single blanket `ANY /api/:rest*` passthrough (attach
`Authorization: Bearer SANDBOX_API_KEY`, forward method/path/query/body)
rather than allowlisting individual routes the way `dashboard/`'s two-route
proxy does. Every new admin route below is reachable with zero additional
proxy glue; the actual authorization decision stays exactly where it
already lives, in `src/router.ts`'s `requireServiceAuth` calls.

   proven live under real concurrent load (8 threads, ~800 searches/sec,
   0 errors/0 empty results across two runs of 1330+1387 queries while
   the alias was atomically repointed) — a genuine, measured zero-downtime
   guarantee. Also found the naive "delete + recreate under the same name"

   deletes any alias pointing at it, and recreating the collection does
   NOT restore the alias — against a stable alias name (how every real
   caller reaches it), that's a **permanent outage**, not a brief

   confirmed live** once corrected mid-investigation (the real switch is
   `PHOENIX_ENABLE_AUTH`, not `PHOENIX_DISABLE_BASIC_AUTH`). Install size
